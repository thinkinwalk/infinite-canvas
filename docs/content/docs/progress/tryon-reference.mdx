# 服装上身优化方案

## 1. 目标与结论

建议把当前工具完善为“指定模特 + 指定服装 + 可选姿势 + 可选场景”的电商试衣工作台。默认保留模特原姿势和原背景，让只想换衣服的用户完成最短流程；有拍摄需求时，再选择姿势和场景。

产品验收优先级建议为：服装一致性、人物一致性、姿势符合度、画面自然度、场景美观度。不要只以画面好看作为试衣合格依据。

技术上先保留现有多图编辑作为评测基线，再评测 FASHN VTON v1.5 的专门试衣，以及 Leffa 的试衣、姿势迁移组合。通用编辑可继续承担创意场景与构图。生产默认路线根据真实素材的合格率和合格图成本决定。

本文是方案，不表示模型已接入、功能已上线或效果已验收。数量与阶段安排是建议，不调整现有上传限制、超时、重试、并发、收费或素材保留规则。

## 2. 当前实现核查

本轮依据用户截图及本地源码核查，没有登录生产环境读取运行配置或提交真实生成。因此，下列实现结论针对本地源码；生产实际模型 ID、渠道、价格与输出质量仍需单独核实。

| 项目 | 当前本地实现 | 优化方向 |
| --- | --- | --- |
| 服装 | 上装、下装两个上传槽，至少一项有图 | 增加连衣裙/连体装；区分平铺图和穿着图 |
| 模特 | 官方图库选择，按分组、性别筛选 | 增加本地上传；后续支持从我的素材选取 |
| 输入校验 | 模特、场景仅接受官方图库 URL | 新增上传来源校验，不能只改前端入口 |
| 姿势 | 只有可选自由描述，没有独立字段 | 原姿势、内置姿势、自定义参考三种入口 |
| 场景 | 官方图库可选 | 明确原背景选项，换场景独立触发 |
| 生成 | 图片按上装、下装、模特、场景顺序进入通用 `/images/edits` | 根据任务分配试衣、姿势或场景处理 |
| 模型 | 种子配置为 `model: default` | 固定并记录实际执行模型、版本和能力 |
| 输出 | 种子配置请求 `1024x1536` | 区分请求尺寸、实际像素、增强后像素 |
| 结果区 | 通用图片结果组件、输入缩略图、下载 | 专用大图、服装细节对比、任务快照 |
| 素材库 | Go 代码固定清单，指向外部 R2 域名 | 建立来源台账与可维护的资产目录 |

主要源码：

- `web/src/pages/cases/index.tsx`：`TryonWorkspace`、`CaseResult`、报价与提交。
- `web/src/services/api/cases.ts`：图库类型、图库请求、案例运行和报价。
- `handler/tryon_library.go`：内置模特与场景目录。
- `handler/cases.go`：试衣输入校验、图片角色提示词、执行与费用处理。
- `handler/case_processors.go`：多图图片编辑请求组装。
- `repository/case_seed.go`：`official-tryon` 输入与默认运行配置。

当前图库代码注释写明清单来自参考项目的公开种子库。不能由“公开可访问”直接判断可以继续用于本站商业图库；建议核实来源与使用依据，并逐步换成本站制作和管理的素材。这里只指出素材来源待核实，不据此判断现有素材已经侵权。

## 3. 页面与操作流程

### 3.1 布局

继续沿用现有主题、导航和左右工作区，不增加营销大图。桌面左侧建议约 360px 参数区，右侧为可放大的结果；在窄屏按参数、结果顺序排列。固定操作区要为内容留出空间，不能遮住最后一项。

左侧顺序调整为：

1. 服装：单件或上下装，上传对应图片。
2. 模特：从图库选择或上传照片，展示所选人物。
3. 姿势：默认保持原姿势，按需选择或上传。
4. 场景：默认保持原背景，按需替换。
5. 输出：只展示当前链路实际支持的构图、比例与数量。
6. 补充要求：折叠或弱化，避免成为主要控制入口。
7. 当前报价与开始生成。

用户最短路径为“上传服装 → 选择/上传模特 → 生成”。姿势和场景不要求逐项操作。

### 3.2 模特

提供“图库 / 上传照片”两个入口。图库沿用缩略图选择，增加全身/半身、站姿/坐姿等与服装展示相关的筛选；现有地区分组可以保留为次级条件。

指定人物路线必须有模特输入；未选择人物时显示缺少项。将来若提供“自动生成模特”，应设为单独模式，并显示实际采用的人物，不能让用户误以为保留了指定身份。

全身服装优先使用全身人物照片；半身照片可以用于半身上衣展示。若用户只有头像却选择全身，先提示身体部分需要生成，不把头像视作完整体型依据。

图库选择与上传都必须显示预览、更换、移除状态。使用上传人物后，结果区也应正确展示它，不能继续仅用图库 `find()` 得到人物。

### 3.3 服装

建议提供“单件 / 上下装”模式；单件品类包含上装、下装、连衣裙/连体装。品类参与真实请求校验和模型映射，不只改变界面标签。

用户选择图片类型：平铺/挂拍、穿着图。可增加识别建议，但保留手动修正；自动识别是否另行收费应由实际实现与报价决定。

输入多人物、多件衣服或拼图时，应让用户指定主体/裁剪后再运行。不要自动进行会改动花纹和文字的服装重绘；服装提取或去皱只作为用户主动选择的预处理。

只有一张正面服装图时，背面、内衬等未拍到的细节不作为可还原信息。背面展示应请求补充对应服装照片；不具备多视角输入能力的路线应说明限制。

### 3.4 姿势

主界面采用“原姿势 / 姿势库 / 上传参考”三种选择，默认原姿势。

首批建议制作约 12 个经过试衣验证的姿势：正面自然站立、轻侧身、单手叉腰、双手叉腰、单手插兜、双手自然下垂、迈步、侧身回头等。先验证手部遮挡少的姿势，坐姿和大幅转身后续开放。

姿势图库必须有示范图、名称、全身/半身、身体朝向、手臂遮挡和适用服装标签。缩略图完整展示动作，避免方形裁切截掉腿脚。使用本站制作且可追溯的样图，不直接复制参考项目展示图作为本站图库。

上传参考照片后，用户预览人物主体；若多人，先选定参考对象。内部按实际模型要求派生关键点图、DensePose 或其他条件，不假定一张骨架图适用于所有模型。

姿势参考只负责动作。人物脸与体型来自模特图；服装来自服装图；背景来自原背景或场景输入。关键点条件有助于隔离参考人物外观，但是否串入其脸、服装和背景仍须通过结果验收。

初版不增加关节拖动编辑器；先验证内置姿势和上传参考的成功率，再判断是否需要更复杂的编辑工具。

### 3.5 场景

明确“保持原背景 / 白底影棚 / 场景库”。自定义场景上传可放入后续阶段。

保持原背景时，尽量少改背景。白底影棚要区分简单背景替换和重新生成光影；需要生成时应计入报价。选择新场景后，优先限制背景编辑区域，再检查人物边缘、接地阴影和服装颜色。

全图重绘作为评测候选，不默认在试衣后再跑一遍。任何后续场景处理都要重新检查脸和衣服，不能只检查背景。

### 3.6 输出与结果

原姿势默认沿用人物图构图；裤装、连衣裙等需要完整展示时给出全身构图选项。构图、镜头视角、人体姿势应分开表达，不能用“姿势”同时隐含裁切和转动相机。

结果区在用户准备素材后展示本次输入，显著标记示例与本次结果。生成中展示真实阶段状态；无阶段事件时显示正在处理，不伪造百分比。

单张结果使用大幅竖图，不放在通用两列方形网格的半列内。输入服装、人物、姿势参考可在侧边或底部查看；姿势变化时使用并排对比，避免用未对齐的滑杆制造可直接对齐的错觉。

提供放大、下载、再次使用参数。后续补充“只换姿势”“只换背景”“保存我的素材”“加入画布”。已存在的浏览器本地资产能力不能描述为新增云同步。

结果必须绑定生成时的输入快照。用户更换衣服或姿势后，旧结果应保留原任务标记或退出当前展示，不能被重新标注为新输入的结果。

## 4. 参考项目的分工

以下信息依据官方仓库和模型卡，详见文末资料。公开模型能力不等于已在本站验证通过。

| 候选 | 官方可核实能力 | 建议定位 |
| --- | --- | --- |
| 现有多图编辑 | 本地已有多图角色输入与编辑调用 | 基线与创意图候选，先核实实际执行模型 |
| FASHN VTON v1.5 [1][2] | 人物与单件服装输入；上装、下装、连体装；平铺和穿着参考；代码与权重标注 Apache-2.0 | 专门试衣候选，先评测保持原姿势的单件任务 |
| Leffa [3][4] | 试衣与姿势迁移；官方展示把试衣结果继续迁移姿势；仓库和模型卡标注 MIT | 完整需求验证与流程顺序对照候选 |
| Qwen-Image-Edit [5][6] | 多图编辑、人物编辑；2509 文档展示关键点条件改变姿势；2511 提供多图编辑与一致性增强 | 姿势、场景编辑候选，固定具体版本与适配器验收 |
| CatVTON / IDM-VTON [7][8] | 专门试衣；官方标注 CC BY-NC-SA 4.0 | 技术对照；未解决授权条件前不列为商业默认链路 |

FASHN 开源 v1.5 模型卡给出的原生输出为 576×864，并列出体型保留不完美、长衣换短衣可能留下原衣痕迹等限制。不能将原生输出宣传为 1K/2K；如接超分，分别记录原生尺寸和增强尺寸，计入耗时和费用并复核细节。[2]

FASHN 的输入包括自动从人物图提取的姿势条件；这不等于公开调用接口提供了任意目标姿势控制。不能仅把目标姿势参数传入就宣称已支持。[1][2]

Leffa 的试衣和姿势迁移是分别调用的能力，不应包装成已经验证的单次三图生成。Qwen 的具体版本、预处理、提示词、多图数量和服务商实现也需单独验证。[3][4][5][6]

各候选的代码、权重、依赖与素材来源分别登记；主仓库许可不能替代依赖条款核查。首版只调查必要组件，不为此新增通用审批流程。

## 5. 生成流程

### 5.1 第一优先：保持原姿势

```text
服装图 + 模特图
    → 输入检查与必要的尺寸/方向归一化
    → 单件试衣
    → 结果检查
    → 按用户选择处理背景或增强
    → 最终结果检查与保存
```

先解决最常见的换衣任务。脸、头发、手、未替换服装和背景作为保留区域；具体采用区域合成、蒙版约束还是模型自身保留能力，按候选的实际接口选择，不能跨模型共用相反含义的蒙版。

### 5.2 第二优先：指定姿势

建议同时测试两种顺序：

```text
A：模特 + 姿势参考 → 目标姿势人物 → 参考原始服装试衣
B：模特 + 服装 → 试衣人物 → 按目标姿势迁移
```

A 的工程动机是让末次服装生成仍能直接参考原始服装，但不是已证实更优。B 有 Leffa 的官方组合示例。用同素材比较两者的人脸、体型、服装细节、动作和成本后再决定。[4]

只有姿势处理无法维持身份，或关键服装区域完全缺失时，应把问题结果展示为待调整，不继续自动叠加多次收费修复。

若预先准备某个内置模特的多个姿势照片，并且用户选择的目标已存在，可直接选择该人物姿势资产再换衣，以减少在线姿势生成。这要求所有姿势确实属于同一身份，并通过人工验收。

### 5.3 上下装

先验证单件，再开放上下装的生产路线。FASHN 公开接口以单件服装及品类为单位，上下装套装不能假定一次请求即可同时解决。[1]

评测先上装后下装、先下装后上装及现有通用编辑一次合成。串联时第二次生成必须检查是否破坏第一件衣服；裤腰、衣摆、塞衣、外套覆盖等规则进入测试集。

没有通过套装验收的引擎只能开放其已验证品类，或明确把套装作为另一候选路线报价。不能把连衣裙拆成上下装。

### 5.4 场景与高清

背景替换和高清增强作为独立可选步骤。优先复用现有能力并核实本任务是否适用，不因为项目已有抠图/超分就宣称组合后质量有保证。

不要默认最后再用通用模型全图“美化”。面料、Logo、纽扣与人物身份是后处理验收重点；后处理失败时保留之前合格的图。

## 6. 接口、资产与任务

### 6.1 请求字段

沿用现有案例运行入口，逐步补充结构化字段。下表是接口设计建议，不要求立刻重做全部案例协议。

| 字段 | 用途 |
| --- | --- |
| `modelImageUrl` / `modelAssetId` | 明确人物输入；来源互斥，实际采用现有资产协议可表示的形式 |
| `garmentCategory` | `tops`、`bottoms`、`one-pieces` |
| `topImageUrl`、`bottomImageUrl`、`onePieceImageUrl` | 当前任务需要的服装；连体装与上下装互斥 |
| `garmentPhotoType` | 平铺/挂拍或穿着参考，按适配器实际枚举映射 |
| `poseMode` | `original`、`library`、`reference` |
| `poseId` / `poseImageUrl` | 姿势库资产或上传参考，与模式一致 |
| `sceneMode` | `original`、`studio`、`library` |
| `sceneImageUrl` / `sceneId` | 已选择场景 |
| `framing`、`aspectRatio`、`count` | 仅开放引擎真实支持的构图、画幅、数量 |
| `prompt` | 补充要求，不代替关键控制字段 |

服务端检查模式与字段组合、用户资产归属、图片可解码和引擎能力。上传模特和姿势应走受控上传/资产流程；不要通过取消 URL 白名单来接受任意外链。

图片角色表统一生成请求顺序和提示词说明，避免前后各维护一份导致“图 3”含义错位。文件名本身不作为所有上游都理解图片角色的依据。

### 6.2 姿势资产

首版在现有图库接口增加 `poses` 即可。每项建议包含 `id`、`name`、`thumbnail`、原始参考、全身/半身、朝向、遮挡标签、适用品类、来源和验收状态。

关键点或 DensePose 等派生资源带预处理版本；只缓存任务真实需要的格式。大图放资产系统，前端业务草稿按仓库约定使用 localforage，不把图片和生成记录放进 localStorage。

跨设备图库与账号云资产属于新增能力，需要独立确定存储、读取权限和删除行为，不能默认当前已有。

### 6.3 模型接入与任务状态

优先复用项目现有模型目录、渠道、功能绑定、报价与任务能力，最小增加试衣及姿势处理所需适配器，不建立第二套模型后台。候选引擎是否已存在协议适配器要在实施时核实。

专用 GPU 模型放在独立推理服务或实际可用的云端服务；主应用负责请求、素材、任务、计费和结果。未核实 GPU 前不将现有生产服务器视作可直接运行这些模型。

多阶段生成建议保存步骤状态、上游任务 ID、输入快照、模型版本、输出、费用及失败原因。刷新或断网后读取任务状态；取消本地等待不等于取消了上游计费。

优先复用已有异步任务机制；若无法表达试衣步骤，再增加小范围数据结构。不要让所有其他创作工具一起重构。

### 6.4 报价与失败

报价需要包含实际路线、模型版本、服装件数、姿势/场景步骤、数量和增强选择，并与提交快照绑定。更换选项导致路线变化时重新报价。

不沿用截图中的固定“10 点”作为新组合流程定价。总成本应包含实际采用的处理步骤和平台服务费；具体数字待模型测量和业务定价。

输入不合格时在收费调用前拦截。部分步骤失败时保留已完成图、区分已完成与未执行步骤，分别记录平台退款和上游实际扣费。不能把平台退款描述为上游没有计费。

首版不默认自动切换模型、自动付费重试或自动增加修复。用户主动重试时，只提交需要重做的步骤，并展示费用。超时、重试次数、上传限制、并发或保留期限若要调整，实施前按仓库规则另行说明并确认。

## 7. 质量评测与上线门槛

### 7.1 样本

建议先准备约 30 组真实业务输入做探索性评测，避免把首批样本通过率当成整体保证。探索阶段筛掉明显不适合的路线，再用独立样本验收。

| 维度 | 样本覆盖 |
| --- | --- |
| 服装 | 纯色、条纹、格纹、印花、Logo、纽扣、拉链、口袋、长短袖 |
| 品类 | 上衣、裤装、半裙、连衣裙；外套叠穿单独验收 |
| 人物 | 不同体型与肤色、长发遮挡、半身与全身 |
| 姿势 | 原姿势、轻侧身、迈步、手部遮挡；坐姿与背面作为困难组 |
| 服装来源 | 平铺、挂拍、另一人物穿着 |
| 特殊变化 | 长袖换短袖、宽松换修身、上下装衔接 |
| 场景 | 原背景、白底、复杂背景 |

### 7.2 验收标准

每张图分别记录：

1. 衣服：款式、领口、衣长、袖型、口袋、图案和关键文字是否一致。
2. 人物：是否仍是指定人物，体型、肤色是否明显改变。
3. 姿势：身体方向、手臂和腿的主要动作是否符合目标。
4. 自然度：手脚、袖口、腋下、腰线、遮挡、边缘和阴影。
5. 输出：实际像素、文件可读、下载和输入快照归属。
6. 成本：总耗时、排队、失败、人工修图时间、总费用。

自动辅助可使用解码检查、人物检测、经过尺度与位置归一化的可见关键点对比，以及适用位置的 OCR。OCR 仅在文字原本清晰可见时作为辅助，不把遮挡或透视造成的差异直接判失败。

不使用单一图像相似度替代服装和身份验收，也不把背景变化计入服装错误。对无真实目标成片的任务，不能把整图 PSNR/SSIM 当成产品合格标准。

最终指标采用“每张人工验收合格图的总成本”，并单独报告首次合格率、完成率、延迟分布和严重服装错误。具体发布阈值在首轮评测后由业务确定，本方案不编造预期成功率。

## 8. 实施顺序

| 阶段 | 工作 | 完成判断 |
| --- | --- | --- |
| P0：核实基线 | 确认实际模型、渠道、图片输入、原始结果、价格；建立样本集 | 能复现当前效果并知道主要失败类型 |
| P1：基础工作台 | 自定义模特、明确原姿势/原背景、连体装入口、真实输入预览、大图结果、输入快照 | 功能进入待测试；用当前实际支持路线验证 |
| P2：专门试衣 | 接入一个最有希望的候选，与现有路线做单件对照 | 按品类确定可开放范围，不一次替换全部任务 |
| P3：姿势 | 内置姿势资产、上传参考、预处理、A/B 顺序评测、异步恢复与步骤报价 | 身份、衣服、姿势同时达到验收要求 |
| P4：拍摄扩展 | 换场景、上下装套装、批量姿势、独立失败重做、资产复用 | 每项分别验收并控制合格图成本 |

P1 可先实现姿势选项所需的数据结构，但未接入和验收目标姿势能力前，不向用户提供可收费执行的空控件。场景、输出比例和数量也遵循相同原则。

按当前代码结构，预计涉及 `TryonWorkspace` 所在页面、案例 API 类型、图库接口、试衣校验与执行、种子配置，以及实际需要的推理适配器。工作台逻辑明显增长后再抽出页面私有文件，避免无关案例跟着重构。

本方案不估计确定工期。实际工作量取决于现有异步任务复用程度、模型渠道可用性、GPU 条件、图库素材准备和首轮效果。

## 9. 建议的第一版范围

第一版先做好：上装/下装/连体装单件、内置/上传模特、原姿势、原背景、大图结果与服装细节核对、真实报价和任务快照。

随后在有验证结果后开放：约 12 个基础姿势及自定义姿势参考。上下装、场景、批量和高清逐项补齐，不同时把所有变量放进一条无法定位问题的链路。

真正需要向用户承诺的是输入可控、结果可对比、费用清楚。人物完全不变、服装细节零误差、任意动作都准确等表述不作为上线文案。
